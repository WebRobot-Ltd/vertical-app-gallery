# vertical-app-gallery

369 vertical applications generated by the **WebRobot app builder** from plain-language functional descriptions: 177 from Italian descriptions (`apps/`) and 192 from English descriptions of UK services (`uk/apps/`). Each app comes with:
- the generated manifest;
- the result of an automated functional test;
- screenshots of the runtime;
- the features it still cannot express.

The purpose is demonstration and research: we want to measure **how general and expressive the `VerticalApp` format is**. To do that, we reproduce the features of real products across very different sectors: legaltech, fintech, HR, travel, healthcare, energy, agritech, media, e-commerce and public administration.

The apps are not copies of existing products. Each description restates the features of a type of service in generic terms, with invented names and no trademarks.

## Method

1. **Description.** We wrote a functional description for each type of service, with no reference to any platform. It covers actors, data, flows, automations, notifications, approvals, pricing and languages. The descriptions are in Italian.
2. **Generation.** The description goes to the app builder, a system agent of the WebRobot platform. It replies with a `VerticalApp` manifest (`webrobot.eu/v1alpha1`). If the manifest fails validation, the builder gets the errors back and fixes them.
3. **Validation.** Every manifest is checked against the schema and against the runtime contract (cross-references, tools, approvals, placeholders). The runtime refuses a manifest that breaks the contract, so a broken app never goes online.
4. **Functional test.** Every app runs on the interpretive runtime, which **interprets the manifest as is**: no code is generated. A script then uses the app the way a person would; see the next section.
5. **Gap analysis.** Whatever the builder cannot express goes into `spec.extensions`.

## Functional test

For each app, the script (`tools/functional_test.mjs`) does the following:
- opens every page with every role allowed to see it;
- checks that other roles and visitors are refused;
- fills in and sends every form;
- checks that each saved record appears wherever its collection is shown, and that back-office records stay hidden from users;
- fills catalogues through the admins' data page;
- starts the agents and the templates and waits for the report;
- fires the triggers;
- exports CSV.

The agents run against a mock of the platform API (`tools/mock-platform.mjs`), so the test checks the app's wiring, not the quality of the AI output.

**163 of 177 apps pass with no failures.** The other 14 fall into two groups.

7 manifests are refused by the runtime contract, for example an access rule that names a role the app does not define. These apps have no screenshots.

The other 7 have design problems:
- 3 apps show data that only an agent writes, but no agent is set up to write it;
- 3 apps open catalogue forms to every user, where they should be for admins only;
- 1 app makes the listed items private to the user who created them, so the people meant to browse them cannot.

Warnings are mostly expected outcomes of a test without real data, such as an empty list after a trigger with nothing to process.

Each app's `functional_test.json` has every check of that app. [`results/functional_test.tsv`](results/functional_test.tsv) lists all checks.

## First round vs second round

The first round (published here earlier) showed where the format, the runtime and the builder fell short. Since then, we added these constructs to the manifest and runtime:
- file upload with text extraction for agents;
- event-driven and date-relative email;
- per-record access rules and roles derived from data;
- per-user API credentials;
- per-plan quotas and quantity-based pricing;
- public forms, booking, maps and CSV export;
- an admins' data page with CSV import.

The functional test also found defects in the runtime itself, all fixed:
- uploads were blocked by the cross-site check;
- drop-downs fed from a collection stayed empty;
- catalogues had no way to be filled.

We then regenerated the 131 first-round apps from the same descriptions, using the updated builder, and compared them with the same static flow analysis (`tools/flows.py`):

| Same 131 apps | First round | Second round |
|---|---|---|
| Apps with flow errors | 67 | 28 |
| Collections read by a view but never written | 114 | 12 |
| Agents declared but never started | 21 | 5 |
| Roles derived from fields that do not exist | 7 | 0 |

The builder now also runs a design check before proposing a manifest: **who fills each collection**. The check flags user data that is shown but never written, and catalogues open to everyone. It flags 10 of the 177 apps.

## Navigation recordings

All 352 valid apps (182 UK, 170 Italian) were also browsed by a recorder signed in as the app's admin: every menu page opened, a form filled and sent, an agent run started. Each app has a `navigation.json` with the pages opened and what was found; [`results/navigation_issues.tsv`](results/navigation_issues.tsv) lists them all.

- **No JavaScript errors and no error pages** in 2,190 pages opened.
- Most empty data pages are expected on a local runtime where agents are mocked: the collections they fill stay empty.
- The recordings found real design defects that the linter now reports: an admin role with no menu page (4 apps) and collections that nothing in the app fills (6 apps).

## Real agent runs in production

Eight UK apps were published on the production platform in a temporary organization, and used as a customer would: a form sent, a trigger starting a real agent (Claude), the agent's result saved in the app. **7 of the 8 flows completed on their own, 42 to 84 seconds from the form to the result** (the eighth agent correctly reported that the app had no building catalogue yet). The runs found four runtime defects, all fixed the same day: field defaults not saved when a form hides the field, a required drop-down that looked chosen but was empty, a trigger goal without the record id, and a read tool that could not list a catalogue.

## What is still missing

These features need new infrastructure rather than new manifest constructs:
- inbound email;
- email campaigns to third parties;
- WhatsApp, SMS and push notifications;
- OAuth to third-party services for each end user;
- audio and video.

The apps that need them declare them in `spec.extensions`.

The first-round gap analysis is kept in `gaps/`. It split every description into elementary features: of 2,566 features, 59% were expressed, 35% were declared not expressible, 4% were only in the agent's instructions and 2% were silently lost. Many of those gaps are closed now; the tables describe the first round.

## Layout

```
apps/index.json                    every app: validity, test outcome, agents, views, extensions, design warnings
apps/<slug>/manifest.yaml          generated VerticalApp manifest
apps/<slug>/README.md              description given to the builder, contract errors, failed checks, extensions, screenshots
apps/<slug>/functional_test.json   every check of the functional test for this app
apps/<slug>/screenshots/*.png      anonymous home, mobile home, then every view as each role
apps/<slug>/navigation.json        pages opened by the navigation recorder and what it found
uk/apps/<slug>/                    the UK round, same layout (screenshots as .jpg), plus the app's sector
uk/results/                        functional test of the UK round
results/navigation_issues.tsv      issues found by the navigation recorder, both rounds
results/functional_test.tsv        all checks of all apps
results/functional_test_summary.tsv  pass / fail / warning per check
gaps/                              first-round gap analysis (see above)
tools/runner.py                    bulk generation through the app builder
tools/tsvalidate.ts                validation against the runtime contract
tools/flows.py                     static flow analysis (who reads and writes each collection)
tools/prepare.py                   test copy of the manifests (agents point at the mock platform)
tools/mock-platform.mjs            mock of the platform API used by agents, email and files
tools/functional_test.mjs          the functional test
tools/shoot.mjs                    screenshots
```

## Notes

- The screenshots come from a fresh test runtime, with test logins and no data. They show structure, navigation and roles, not content.
- The vertical-kit runtime and the app builder are part of the WebRobot platform and are not included here. The scripts in `tools/` document the procedure and need the runtime to run.
- Manifests that fail the contract and apps that fail the test are published anyway, because they are part of the result.
- App names, descriptions and UI copy are in Italian for `apps/` and in English for `uk/apps/`, the languages the apps were specified in.
