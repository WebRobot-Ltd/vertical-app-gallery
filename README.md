# vertical-app-gallery

176 vertical applications generated by the **WebRobot app builder** from plain-language functional descriptions. Each one comes with the generated manifest, screenshots of the runtime, and an analysis of what the manifest cannot express yet.

The purpose is demonstration and research. We want to measure **how general and expressive the `VerticalApp` format is** by reproducing the features of real products across very different sectors: legaltech, fintech, HR, travel, healthcare, energy, agritech, media, e-commerce and public administration. The apps are not copies of existing products. Each description restates the features of a type of service in generic terms, with invented names and no trademarks.

## Method

1. **Description.** We wrote a functional description for each type of service, covering actors, data, flows, automations, notifications, approvals, pricing and languages, with no reference to any platform. The descriptions are in Italian.
2. **Generation.** The description goes to the app builder, a system agent of the WebRobot platform, which replies with a `VerticalApp` manifest (`webrobot.eu/v1alpha1`). If the manifest fails validation, the builder gets the errors back and one chance to fix them.
3. **Validation.** Every manifest is checked twice: once against the schema, and once against the runtime contract (cross-references, tools, approvals, placeholders).
4. **Interpretive runtime.** Valid apps are served by the vertical-kit runtime, which **interprets the manifest as is**. No code is generated. The screenshots show the home page on desktop and mobile and every view, with test logins and no data.
5. **Gap analysis.** Whatever the builder cannot express goes into `spec.extensions`. On top of that, every description was split into elementary features, and each feature was compared with the manifest.

## Layout

```
apps/index.json                 list of apps with status and counts of agents, views and extensions
apps/<slug>/manifest.yaml       generated VerticalApp manifest
apps/<slug>/README.md           description given to the builder, remaining errors, extensions, screenshots
apps/<slug>/screenshots/*.png   anonymous home, mobile home, one screen per view
gaps/feature_gaps.tsv           44 gap categories: class, apps affected, proposed construct
gaps/all_gaps_by_category.tsv   categories ranked by number of apps (extensions + per-feature analysis)
gaps/extensions_labeled.tsv     every spec.extensions entry with its category
gaps/features_per_app.tsv       every elementary feature of every description, with outcome and manifest reference
tools/                          scripts used: bulk generation, validation, screenshots
```

The gap tables use four classes:
- **a**: already expressible, but the builder did not know it.
- **b**: the schema lacks a construct.
- **c**: the construct exists, but the runtime does not execute it yet.
- **d**: out of scope (regulated or physical activities).

## Notes

- The internal screens are empty because the runtime runs without data. They show structure, navigation and roles, not content.
- The vertical-kit runtime and the app builder are part of the WebRobot platform and are not included here. The scripts in `tools/` document the procedure.
- Manifests with remaining errors are published anyway, because they are part of the result.
- App names, descriptions and UI copy are in Italian, the language the apps were specified in.

This is the first round. We fix the gaps in the schema, the runtime and the builder's instructions, then regenerate the same descriptions to measure before and after.
